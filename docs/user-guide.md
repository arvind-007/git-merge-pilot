# User guide for project managers

git-merge-pilot reads every pull request (PR) in your projects and explains it in plain language:

- what it changes
- what might break
- whether it touches security-sensitive code
- whether it overlaps with other work
- whether it's ready to merge

You don't need to read code to use it. The technical evidence is there for when you need to ask a developer a precise question.

git-merge-pilot only **reads** from GitHub. It never comments on, approves or merges anything, so the decisions stay with your team.

## Where to look

| Page               | Use it for                                                                                |
| ------------------ | ----------------------------------------------------------------------------------------- |
| **Overview** (`/`) | Open PRs across everything you can see, risk distribution, recent important findings      |
| **Projects**       | One project's PRs, risks and overlaps                                                     |
| **Risk center**    | PRs at high or critical risk, open security and breaking-change findings, active overlaps |
| **Developers**     | Who has what open, and how much is waiting for review                                     |
| **Notifications**  | Alerts and the daily digest                                                               |

Members see only the projects they've been added to. Admins see everything.

## Reading a PR report

A report opens with the **headline**:

- overall risk level
- the recommendation
- the confidence score
- any banners. For example, "Generated without AI" or "AI budget reached" mean the narrative is shorter, but all the checks still ran.

The report has these tabs:

| Tab                  | What it tells you                                                                                                                                      |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Summary**          | Executive summary, business impact, affected areas (modules, services, APIs, DB tables, integrations, config, infrastructure), and recommended actions |
| **Risk**             | Score per risk dimension with reasons and evidence, and merge readiness with its blockers                                                              |
| **Breaking changes** | Things that could break other code, services or clients                                                                                                |
| **Security**         | Secrets, risky code patterns, scanner results, GitHub security alerts                                                                                  |
| **Related PRs**      | Other PRs touching the same files, functions, APIs, tables or config, or doing the same work                                                           |
| **Tests & deploy**   | Tests added or changed, missing tests, CI status, migrations, env and config changes, deployment ordering, rollback difficulty                         |
| **History**          | How the analysis changed with each push: new, unchanged and resolved findings                                                                          |

Each finding has the following parts:

- a plain-language **description**
- often **what might break**
- a **recommendation**
- **evidence**: file and line links that open GitHub

If you need to discuss a finding with the team, share the evidence link.

## Verified vs potential

This is the most important distinction in a report.

- **Verified** (solid badge): a fact established by deterministic analysis or GitHub data. For example, "the function `createOrder` was removed while still exported", "a migration drops column `email`", "the CI check `test` failed", or "a string matching an AWS access key was added". Verified items have exact evidence.
- **Potential concern** (outlined badge): an inference by the AI. For example, "this change to discount rounding may affect invoices generated by the billing service". These are useful prompts for a conversation, not facts. Ask the author to confirm.

git-merge-pilot never says a PR is "secure". "No security findings" means none of the checks found anything, not that there is nothing to find.

## Risk scores

Risk is scored from 0 to 100 on six dimensions:

| Dimension           | Rises with                                                                                                             |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **Security**        | secrets, injection-prone code, weakened TLS or crypto, risky CI workflow changes, auth changes, security alerts        |
| **Breaking change** | removed or renamed public functions, changed signatures, removed or changed API routes, schema drops, env var removals |
| **Integration**     | changes to contracts other services or repositories use; overlaps with other open PRs                                  |
| **Regression**      | size and spread of the change, core modules touched, missing tests                                                     |
| **Database**        | migrations, especially destructive or locking ones                                                                     |
| **Deployment**      | new env vars, config or infrastructure changes, required deployment ordering                                           |

| Score  | Level        |
| ------ | ------------ |
| 80–100 | **critical** |
| 60–79  | **high**     |
| 30–59  | **medium**   |
| 0–29   | **low**      |

The **overall risk** is the highest of the dimensions. It is raised to at least **high** whenever there is a verified critical or high security finding. Every score comes with a rationale and evidence. When AI is enabled, it may adjust a score by up to 15 points and must explain why.

**Confidence** (0–100) says how complete the analysis was. It is lower for very large PRs (diff truncated), for languages with only basic support, or when AI was unavailable. The **Limitations** list explains why.

## Recommendations

Exactly one recommendation is given. The rules below are checked in order, and the first match wins.

| Recommendation          | Meaning                                                                                                                       | What you can do                                             |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| **Escalate**            | A critical security issue or a critical breaking change without mitigation                                                    | Bring in a tech lead or security owner before anything else |
| **Changes required**    | Required checks are failing, or a reviewer requested changes                                                                  | Wait for the author to address them                         |
| **Needs clarification** | Open questions or ambiguities, for example unclear intent or a possible duplicate of other work                               | Ask the author the listed questions                         |
| **Merge after checks**  | Fine in principle, but blockers are listed: pending checks, missing approvals, migrations, cross-repo dependencies, high risk | Track the blockers, and plan deployment order if needed     |
| **Ready to merge**      | No blockers found                                                                                                             | The team can merge per its normal process                   |

Recommendations are advice. Your branch protection rules and reviewers still decide.

## Related PRs (overlap)

Relationships have a confidence level:

- **Confirmed**: definite. For example, both PRs edit the same lines, or one explicitly depends on the other.
- **Likely**: strong signal. For example, the same function or the same database table.
- **Possible**: weak or AI-suggested. For example, two PRs that seem to implement the same thing. Treat these as questions to ask.

Cross-repository overlap is shown too. For example, PR A changes an API route and PR B, in another repository, calls that route. A **suggested coordination** note (merge order, who should talk) appears when it's useful.

## Updates and history

When a developer pushes new commits, the PR is re-analysed:

- If the change is small, only the new commits are analysed.
- Findings are marked **New**, **Unchanged** or **Resolved**, so you can see progress.
- You get notified only when something meaningfully changes: the risk goes up, a new high or critical finding appears, or a new confirmed or likely overlap appears.

## Notifications and the daily digest

Admins configure the following:

- which severities trigger alerts (default: high and above)
- the channels: in-app, email, Slack
- quiet hours, when non-critical alerts wait until morning
- the daily digest time per project or for the whole organization

The digest summarises:

- new and updated PRs
- risk changes
- new overlaps
- PRs that are ready to merge or waiting for clarification

## FAQ

**A report seems wrong.** Check whether the item is Verified or a Potential concern. Potential concerns can be wrong. Verified items link to their exact evidence. If a verified item is wrong, an admin can correct the repository profile (for example, where migrations live), or report a false positive to the maintainers.

**A PR hasn't been analysed yet.** Large PRs and first-time indexing take a few minutes. If it's stuck, ask an admin to check **Settings → System status**, or to use **Re-analyze**.

**Why is a repository missing?** It may not be monitored, may not be in your project, or the GitHub App may not be installed on it. Ask an admin.
